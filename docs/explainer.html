What the event taught

  • An exact 0.0 from Pauli-path means "the method could not see it". It does not mean the true value is zero. This cost a wasted upload on G2 and hid G3's answer for hours.
  • Try every transpilation level early. Level 3 was the single biggest gain (G3 from 320 to 720, G4 from 400 to 700), and the sample circuit had suggested it was the worse setting.
  • Check that a method's values hold still before trusting them. On G2 the MPS values barely moved between chi 16 and 24, so they could be combined. On G3 they flipped sign, so they were noise.
  • A server limit can belong to one qubit. The kit priced every run using qubit 0, whose limit was a threshold of 7e-5. Other qubits accepted 3e-5.
  • Extrapolation has a range. On G4, extending the straight-line trend to zero truncation gained 100 points. A log fit pushed to 1e-5 lost them again (700), and so did a file of measured 3e-5 values (700).
  • The coupon was never usable. Every paid job was refused as "not enough funds" with nothing charged, so all results came from free settings.

The push for 900 on G4

The kit had priced every run on qubit 0, whose floor is 7e-5. Priced qubit by qubit, 14 qubits accepted 3e-5, 4 accepted 4e-5 and 2 accepted 5e-5. Those runs took about 30 minutes each, against about 5 at 7e-5.

The measured values agreed 0.99 with the 800 file, and a file built from them scored 700. The last 100 points probably need finer pruning than BlueQubit allows [Guessing].

In the last hour, an average of G2 over chi 21 to 24 scored 540 again, and a G4 file extended from each qubit's two finest runs scored 700. A real quantum computer was ruled out: BlueQubit's quantum device gave no price on this account, and at 1,956 to 7,296 two-qubit gates, hardware noise would leave too little of the signal for near-exact values.

Two more lessons

  • Check caps where they're enforced. The scheduler had passed a $10 per-run cap, above the $2 rule, and the kit has no ask-first check of its own. It was set to $2 before the only paid-device try.
  • No score fitting. Every upload was one method or a stated extrapolation, built without using site scores, to stay inside the event's rule against probing.
Understand

The puzzle, the score and the methods

  • Each qubit is a coin. ⟨Z⟩ says how hard it leans to heads: +1 is always heads, −1 always tails, 0 a fair flip. Every ID asks about one coin. Midwest_G2_7 means qubit 7 of circuit G2.
  • The circuit is a card trick. It shuffles the deck (U), drops dye on one card (the x kick on the butterfly qubit), then runs the exact same shuffle backward.
  • If the dye never reached qubit q, the backward shuffle puts q right back where it started and its coin reads +1. The more dye reached q, the further its ⟨Z⟩ falls from +1.
  • The dye spreads like a ring on water, about one neighbor per layer of gates. That ring is the light cone. Qubits outside it read +1 for free.
  • Order 2 runs the trick twice with a z flip on the probe qubit in between. The answer then depends on finer detail, so shortcuts lose more accuracy.
order 1 |0…0⟩→ U shuffle→ x on butterfly→ U backward→ read ⟨Z⟩ on qubit q
order 2 |0…0⟩→ U→ x→ U backward→ z on probe q→ U→ x→ U backward→ read ⟨Z⟩ on q

How the site scores you

  • For each circuit: corr² between your numbers and the exact ones, times that circuit's points. A negative correlation scores 0.
  • Scale and offset don't matter. Double every value, or add 0.3 to all of them, and corr² stays the same.
  • Sign and qubit order do matter. Flip the sign or shuffle the rows and the score collapses. Qubit 0 is the rightmost letter of a Pauli string, and the kit handles that.
  • You get 10 uploads per problem and the best one counts.

Set up

Setup, step by step

The kit is one folder on your Mac: ~/Downloads/bluequbit-hackathon-kit. Claude Code started inside it becomes the captain, because it reads the CLAUDE.md in that folder and finds the 4 agents next to it.

  1. Python packages. Already installed on this Mac: qiskit 2.6.2, qiskit-aer 0.18.4 and bluequbit 0.19.1b1. On a fresh machine, run pip install -r requirements.txt.
  2. API token. Already set in your terminal as BLUEQUBIT_API_TOKEN. The kit hands it to BlueQubit's SDK and never prints it. Never paste it into a chat.
  3. Mode. BQ_MODE=rehearsal switches the kit to the offline practice backend. Without it, the kit talks to your real account. At kickoff run unset BQ_MODE to be sure.
  4. Captain. cd ~/Downloads/bluequbit-hackathon-kit, then claude.
  5. Control panel. In a second terminal, in the same folder: python kit/dashboard.py. It opens http://127.0.0.1:8765/ in your browser.
  6. Check. python kit/bq_kit.py status should print mode=live prefix=Midwest spent=$0.000 of $25.00 budget.

Options for --opt: chi is the MPS bond dimension (up to 2048 on cpu), th the Pauli-path threshold (1e-5 and up, required above 13 qubits), level the Pauli-path transpilation level, 0 to 3.

The control panel

A local web page at http://127.0.0.1:8765/ that reads the work/ folder every 5 seconds. Only your browser on this Mac can reach it. Start it with python kit/dashboard.py, or add --rehearsal for practice. Stop it with Ctrl-C in its terminal; if a run it started is still going, it waits for that run first.

The top bar

  • Mode banner. Blue REHEARSAL means offline, no money. LIVE means your real account and real money.
  • Spend vs budget. A bar with a tick at 80% and a note about the $2 ask line.
  • Pending jobs. Jobs waiting for collect, and how many jobs are in the ledger.
  • Job slot. Free or busy. Busy means a run or collect is going, started by an agent or by this page. Paid runs and collect from the page are blocked while it's busy.

Circuits tab

One row per circuit: qubits, 2q depth, order, points, number of CSVs, uploads used out of 10, and the best score you've logged. Click a row to open its detail:

  • Buttons: Run candidates, Paid run, Estimate, Log upload, and Rehearsal score in practice mode.
  • Candidate CSVs. Every file with its corr² against exact (samples only), its highest agreement with anything already uploaded, an "uploaded" chip, and a near-duplicate warning above 0.995. Each row has Copy path, Validate and Log upload.
  • Agreement heatmap. corr² between every pair of files; darker means closer. A blend always agrees well with its own inputs, so a dark blend cell proves nothing.
  • Per-qubit chart. Each file's values z-scored, so scale and offset drop out just as they do in scoring. Lines that track each other agree. A mirror image means a sign flip, and a shifted pattern means a qubit-order problem.
  • Spend on this circuit, by setting.

Jobs tab

Spend by circuit, spend by circuit and setting, and the full ledger, newest first: time, qubit, setting, status, value, cost and job id.

Docs tab

circuits.md, tuning.md, picks.md and submissions.md, rendered so you can read the agents' reports without opening files.

Actions tab

  1. Paid run. Pick the circuit, device, options (chi, th, level), qubits (blank means all) and a max cost, then press Check cost. That runs only the free estimate.
  2. The confirm panel shows the exact command, how many qubits will run (ones already done are skipped), the estimate, the cap, what's spent and where the budget lands after the run.
  3. Typing the circuit name unlocks the Run button when the estimate or cap is above $2, when spend would pass 80%, with --no-wait, or when no estimate came back. Otherwise one click runs it.
  4. The check expires after 10 minutes, and the server re-checks spend, budget and the job slot at the moment you confirm.
  • Collect. Gathers --no-wait results. Blocked while the job slot is busy.
  • Log an upload. Circuit, file, the score the site showed and a note. It adds a row to submissions.md and refuses an 11th upload for a circuit.
  • Free commands. A card for each of status, info, points, describe, exact, local, estimate, candidates, validate, score, build and blend.

Console

The bar at the bottom shows the last command and its exit code. Open console to see the streamed output of everything the page ran.

Safety built in

  • It listens on 127.0.0.1 only, needs a key that changes every launch, and refuses requests from other websites.
  • In practice mode every command it runs gets BQ_MODE=rehearsal and an empty token, so it can't reach your account.
  • It never uploads anything and never shows the token.

Method checklist

  1. For each graded circuit, run the free estimate on cpu. If the exact device takes that size at a fair price, run it first.

How realistic is this?

Carries over to live

  • The whole pipeline: IDs, qubit order, CSV format, validate, the spend ledger, one job-submitter at a time.
  • The judge's lessons. A blend of good and weaker loses to the good one. Agreement between two settings of one method can mislead: S3's chi 16 and chi 64 agreed only 0.949, yet chi 64 was 0.993 accurate.
  • The trends. Pauli-path falls off with depth and order 2. MPS needs more chi as circuits grow.

Doesn't carry over

  • Size. All 5 practice circuits fit exact simulation, so everything maxed out. The kit's own tiers expect live circuits past 26 qubits. [Guessing] until kickoff.
  • Money. Practice prices come from a made-up formula in kit/fake_bq.py. Live prices come from BlueQubit.
  • Time. Practice jobs ran on this Mac with no queue. Live jobs wait in a queue, with a parallel-job limit and GPU cooldowns.
  • Engines. The practice MPS is Qiskit Aer and the Pauli-path is a small Python stand-in. BlueQubit's engines will trade accuracy for settings differently.
  • --no-wait. In practice a job finishes inside the submit call. Live, it really runs in the background.

Verdict: the process is well rehearsed. The scores, costs and run times are not a forecast for Saturday. Retune on the live samples before trusting any setting.

What changed in the kit

The spending-cap fix is in kit/bq_kit.py. The original is kept untouched as kit/bq_kit_v1.py.

Runs that wait for results used to check the cap only after each batch of 8 jobs, so one batch could blow past it.

  1. Before each batch, the kit prices the next qubit from real costs already paid at that exact setting.
  2. With no real price yet, it runs 1 qubit first to learn it.
  3. It sizes the batch to fit what's left under the cap and the budget.
  4. It stops before the batch that would pass either one. In the test, a $0.002 cap that used to end at $0.0032 now stops at $0.0020.

Runs with --no-wait used to ignore the cap completely, because those jobs report no cost until collect.

  1. The kit now projects the whole run before submitting anything.
  2. It uses real prices when it has them. Otherwise it uses BlueQubit's estimate and prints a warning, since the estimate may ignore chi and th.
  3. It submits only the qubits that fit under the cap and the budget.
  4. Jobs waiting for collect now count against the budget, and rerunning skips them instead of paying twice.

The rehearsal's work/ folder moved to work_rehearsal_2026-11-20/, because practice spend was showing up as live spend. Live status now reads $0 of $25.
